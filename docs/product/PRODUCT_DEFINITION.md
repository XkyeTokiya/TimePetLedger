# Product Definition

## 文档依据与职责

本文件回答“我们做什么？”。唯一产品 / 领域 Source of Truth 为 [领域提案](../../time-ledger-domain-model-v4-proposal.md)（下文按章节引用）。本项目按 Greenfield 执行；源文档的历史实现讨论不构成本项目工作范围。未决事项统一见 [OPEN_QUESTIONS](../domain/OPEN_QUESTIONS.md)。

## Product Definition

Time Pet Ledger 是一个回顾式个人时间账本。它帮助用户以尽可能低的输入成本还原一天，不要求所有时间精确，但对睡眠和目标相关时间保持更高的记录优先级与时间确认要求。用户在时间事实之上区分推进、卡住与恢复，通过每日复盘留下下一次能够开始的一步。

基础事实是时间。系统追求对时间的真实理解，而不是对每一分钟的精确监控。（来源：§1、最终定义）

## Core User Problem

用户需要大致解释一天怎么过去，却未必能精确回忆每个边界或每段活动。强迫精确、强迫分类或强迫解释原因，都会增加补记成本，甚至诱使用户编造内容。

目标相关时间也不等于明确推进时间：“好像做了一整天”无法区分用户确认的推进、尝试中的阻力，以及尚未做节奏解释的时间。记录与统计需要帮助用户理解这种差异，并找到下次接续行动的入口。（来源：§2、§7–10、§13、§15–16、§18–22）

## Core Loop

1. 优先确认睡眠：每天首次打开时优先确认昨晚几点睡、今天几点醒；已经记录则不重复打扰。
2. 回顾补记：系统根据账本提出可修改的时间区间，用户主要回答“刚才这段时间在做什么？”。普通时间允许模糊。
3. 处理空白：从时间线尚未记录的区间补一笔；想不起来时明确标记为 Unknown，这段时间便已交代。
4. 解释目标时间：需要时关联 Goal、附加推进 / 卡住 / 恢复解释，并可留下接续点；这些不是所有记录的前置条件。
5. 理解与行动：查看由事实派生的睡眠、账本与目标节奏描述，通过每日复盘留下明天第一步，使下一次启动更容易。

这是产品闭环，不额外规定必须依次完成的流程门槛。（来源：§20–22、§26–30）

**记录交互补充（2026-10-05，用户决定，基本设计已认可）：** 活动初版优先问答引导，依次询问节奏、事项、时间；长期目标持续可见，常用目标由用户指定，每笔可更换或取消关联。表单可在设置中切换；时间调整提供完整无需键盘路径，基础组件优先MD3。上述闭环描述不规定实际提问顺序；节奏与目标仍可省略。见[Q-025 / Q-026](../domain/OPEN_QUESTIONS.md#q-025)及[三幕交互规格](../planning/GUIDED_RECORDING_DESIGN.md)。当前仅完成文档同步，原型、组件体验与实现验收仍独立。

**记录交互调整（2026-10-10，Q-047）：** 活动记录主流程改为事实优先：先回答“这段大概在做什么”，时间由系统建议（可调整），保存即成立；Goal 与 Rhythm 移至保存后的轻量理解层。已选择目标后，“整体状态”（推进 / 卡住 / 恢复 / 暂时说不清）要求必选；“暂时说不清”不写入解释、不改变数据模型，其余补充均可留空。三幕顺序及旧交互规格仅作历史追溯，见[Q-047](../domain/OPEN_QUESTIONS.md#q-047)。同日实现调整：活动入口统一为底部记录面板，原“表单可在设置切换”与记录方式设置一并移除（睡眠不变）。

**常用目标补充（2026-10-06，Q-025）：** 成功归档 / 删除所选常用目标后清除常用选择，恢复目标后需用户手动再设；不自动选择另一个目标，不改写原记录或当前会话输入自身关联。

**未完成输入补充（2026-10-08，Q-012）：** 产品只向用户表达填写与正式保存。离开页面时系统可在当前会话内保留已修改输入；同一入口再次进入先询问继续或重新填写 / 编辑。不向用户展示草稿状态、列表、数量或开关；冷启动、进程重启和Web刷新不恢复旧输入。

## Product Boundaries

**记录反馈补充（2026-10-05）：** 当前回顾式时间统一approximate，不提供精度选择。活动记录目标文字用虚线提示编辑，适用节奏子选项增加独立页且仍可留空，移除计数和时间页回改摘要。当前可评审稿见[前端交接](../planning/UI_REBUILD_PLAN.md)，决定见[Q-030](../domain/OPEN_QUESTIONS.md#q-030)；旧exact数据处理待Q-031，未改正式实现。

产品不是：

- timer-first app：主行为是做完一段后回来补记。
- task manager：Goal 仅承载时间归属，不承载任务树、截止日期、百分比、里程碑或优先级。
- habit tracker：习惯连续天数、失败天数不进入当前核心模型。
- productivity scoring system：不生成生产力、效率或完整度成绩，不以数据库枚举或 AI 替用户评价是否“有效”。
- minute-perfect tracking system：完整意味着主要去向基本可解释，也允许未知与近似。

当前核心模型也不纳入详细活动分类、多任务并行分摊、所有 Goal 的每日计划或因果式睡眠分析。睡眠质量、睡眠趋势及更结构化的复盘字段不构成第一版必需能力。描述性关联不能被表述为因果结论。（来源：§1–2、§4、§10–11、§19、§21–22、§25、§30–32、§38）

## Core User Questions

| 用户问题 | 事实或解释来源 |
| --- | --- |
| 我昨天大概是怎么过的？ | TimeBlock + SleepSession |
| 我昨晚睡了多久、什么时候睡的？ | SleepSession |
| 我实际上花了多少时间在这个目标附近？ | TimeBlock.goalId |
| 其中多少是真正推进、多少是在卡住？ | RhythmAnnotation |
| 我下一次从哪里开始？ | continuationHint + DailyReview.tomorrowFirstStep |

来源：§37。对象定义见 [DOMAIN_MODEL](../domain/DOMAIN_MODEL.md)，产品原则见 [PRODUCT_PRINCIPLES](PRODUCT_PRINCIPLES.md)。

目标投入问题在详情中以柱状图 / 热力图展示（Q-033）：近7天含今天、本自然周或本自然月，今天只计已发生时间；底部默认约5条此前记录。它是TimeBlock.goalId的描述性汇总，不增加目标计划或评分能力。当前只设计原型，具体布局与待评审选择见[前端交接](../planning/UI_REBUILD_PLAN.md)。
